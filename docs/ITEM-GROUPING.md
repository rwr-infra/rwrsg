# 物品识别与聚合规则

本文规定 rwrsg 如何判断「这是不是同一个东西」，以及存档数据如何保持向后兼容。
规则与隔壁 rwrops（数据源 + 百科）一致，改动时请两边同步。

---

## 1. 身份用哪个字段

一条售卖物记录长这样：

```json
{ "key": "aav7_turret", "itemKey": "aav7_gl.weapon", "name": "AAV7 榴弹", "price": 300, "num": 1 }
```

| 字段 | 含义 | 是否唯一 |
| --- | --- | --- |
| `key` | **hud 图标名**（`aav7_turret`）。决定渲染哪张图，也是历史上一直写入存档的字段 | ❌ 不唯一 |
| `itemKey` | **记录键**（`aav7_gl.weapon`），对应游戏数据里的那一条记录 | ✅ 唯一 |

### 为什么不能只用 `key`

classic 包里有 **948 条记录，却只有 510 个 hud 图标**：

- 69 个图标被多条记录共用，涉及 **507 条记录**（超过一半）
- `aav7_gl.weapon` 和 `aav7_mg.weapon` 都是 `aav7_turret`
- 87 条 `grinch_*` 记录全都是 `vest_hole1`

**后果**：以图标作为身份时，勾选 `aav7_gl` 会让旁边的 `aav7_mg` 一起亮，
而且一组里只能有一个进售卖列表（去重把其余的都丢掉了）。

### 规定

- **选取、去重、排序、删除、React key —— 一律用 `itemKey`**（`inventory.js` 的 `rowId()`）。
- **`key` 只用来找图**，永远保留「hud 图标名」这个含义，不得改作他用。

---

## 2. 聚合：什么时候多条记录其实是同一个东西

游戏数据里有两条关系，明确说明「这些是同一样东西的不同形态」：

| 关系 | 字段 | 含义 | classic 包实测 |
| --- | --- | --- | --- |
| 武器配置 | `weapon.next_in_chains` | 同一把武器的多种配置（互相指向）。`ac556.weapon` ↔ `ac556_b.weapon` 是同一把枪带不带刺刀 | 131 把武器 → **65 组**（其中 82 组是两两一对） |
| 降解链 | `carry_item.transform_on_consume` | 物品被消耗后变成什么。`snowman` → `snowman_2` → … → `snowman_45` 是一个雪人越用越破，不是 45 件物品 | 472 件物品 → 链条最长 **46 节** |

合计：**110 组，覆盖 599 条记录**。

### 代表项怎么选

一组里显示哪一个，按以下顺序：

1. **没有入边的那个** —— 最完好的形态（`snowman.carry_item`，不是 `snowman_17`）。
2. 若一组里所有成员都有入边（武器配置是互相指向，必然如此），取**字典序最小**的键，
   保证同一份数据每次跑出来都一样，不随包或顺序变化。

### 规定

- 列表/选择器**默认一个组一张卡**，卡片上标注 `N 种配置`（武器）或 `N 种状态`（装备）。
- 卡片上的标注可以**点开**，进入该组看全部成员；进组后仍可单独选取某一个形态。
- 关掉聚合开关时展示全部记录，用于排查。
- 跨包查看时，**只在当前可见的记录范围内聚合**：某个包的切片里链条可能只有一半，
  这是正常的，不要为了凑整而引入包外的记录。

## 3. 存档数据的向后兼容

存档位置：`localStorage` 的 `data` 键，以及用户导出的 JSON 文件。
**任何时候都不得让旧存档打不开、丢字段或改变含义。**

### 历史上出现过的三种形态

| 时间段 | `key` 里存的是什么 |
| --- | --- |
| 2025-08 → 2025-12-29 | PNG 文件名（= hud 图标），如 `aug` |
| 2025-12-29 → 2026-01-31 | 记录键，如 `aug.weapon` |
| 2026-01-31 起 | 又是 hud 图标，如 `aug`；另加 `itemKey` |

中间那段切换时**没有做迁移**，所以那批存档的图片一直是坏的
（程序去找 `assets/items/aug.weapon.png`，这个文件从来不存在）。

### 规定

1. **读取时解析，不重写**。`inventory.js` 的 `resolveInventoryRow()` 把旧键映射到
   当前形态；映射不出来的行**原样返回**，名字/价格/数量一个都不动。
2. 解析顺序（越靠前越可靠）：
   1. 已存的 `itemKey` 仍能解析 → 直接用它；
   2. 存的 `key` 本身就是记录键（`aav7_gl.weapon`）→ 用它；
   3. `key` 能解析成图标 → 取该图标的**第一条**记录（是猜测，但确定且可复现 ——
      旧数据本来就没记下来是哪一个）。
3. **只允许补 `itemKey`，不允许删字段、改字段含义**。`key` 永远是 hud 图标。
4. 旧导出文件（没有 `itemKey`）必须能正常导入；新导出文件在旧版本里导入时，
   最多丢失 `itemKey` 的精度，不能报错。
5. 需要「改数据结构」时，先写清旧形态长什么样、怎么识别，再动手。

## 4. 在线数据源的包（package）

rwrops 的数据站有 22 个包。它们不是「同一份数据的子集」，而是**不同的数据集**，
这一点决定了下面几条规矩。

### 规矩 1：在线包必须和内置快照同源

内置 `data.json` 是从 **vanilla** 抽的，所以在线层默认也必须是 `vanilla`。

**为什么不能随便挑一个包**（真实踩过）：`classic` 里

| 记录 | vanilla | classic |
| --- | --- | --- |
| `vest2.carry_item` | `Vest, type II`，transform → `vest2_2` | **`Health, 150%`**，transform → `Health, 140%` |
| `vest2_2` | 存在，transform → `vest2_3` | **不存在** |
| `vest2_3` | 存在 | **不存在** |

于是 `Ⅱ型防弹背心` 的降解链在 classic 下**没有任何一条边**，聚合不出东西 ——
表现为「二型防弹衣没聚合上」。换成 vanilla 后立刻变成一组 3 个状态。

另外 classic 也不是超集：它比 vanilla 少覆盖 2 个 rwrsg 认识的键，多出来的 15 个
hud 图标对应的是 rwrsg 没有中文名的物品。

### 规矩 2：三种范围，含义必须诚实

选择器里的三个层级：

| 选项 | 内容 | 是否任何包的超集 |
| --- | --- | --- |
| **全部物品**（默认） | 内置快照 + 在线默认包的条目 | ❌ **不是** |
| **合并全部包** | 全部 22 个包的并集 | ✅ 是 |
| 某一个包 | 该包的条目 | — |

「全部物品」不是超集，这一点必须让用户看得出来：`man_vs_zombies` 有 1258 条记录，
比「全部物品」还多。**所以不要把它叫「全部包」** —— 那是错的，用户会发现
单选一个包反而比「全部包」显示得多。

实测（grouped 后的卡片数）：全部物品 627 / vanilla 619 / ww2_base 355 /
man_vs_zombies 640 / **合并全部包 984**。

### 规矩 3：并集很贵，所以是显式选择

`packages.json` 只有计数，`metadata.yaml` 只有 297 字节的统计，**唯一**的每包物品来源
是那个包的 `result.json`，约 4 MB × 22 ≈ **88 MB**。因此：

- **不默认加载**，只在用户显式选「合并全部包」时才开始；
- **并发 6** 路拉取，边到边合并、边显示进度，不是等全部下完才出现；
- 结果**缓存 1 天**（约 220 KB，只留 key / 英文名 / hud 图标 / 链关系）；
- 合并时**先到先得**：基础层不会被后来某个 mod 重定义的同一个键覆盖。

### 规矩 4：缓存必须按包和形状区分

在线缓存的键要同时校验**包名**和**形状版本**。只校验形状时，改默认包不会有任何效果
（旧包的缓存还在 6 小时有效期内），表现为「改了默认包但数据没变」——
这正是「二型防弹衣没聚合上」的另一半原因。
